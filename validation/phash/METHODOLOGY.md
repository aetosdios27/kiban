# Interpretation and limits

This experiment tests a proposed immutable SST point lookup. It makes no changes to the engine. All results come from a standalone Rust crate and private copies of the prepared databases. There are no writes in the measured workloads and the memtable is empty.

The per-SST layout uses real prepared SSTs, not a globally regrouped synthetic table. Each SST is parsed and CRC-verified outside lookup timing. Prefix-compressed blocks are decoded into a contiguous arena retaining their original block boundaries and SST membership. Each decoded record stores the full key, value, and two u16 lengths. This intentionally removes restart decoding and omits version metadata. It is an idealized alternate immutable block representation, not direct indexing into today's compressed entry bytes. The slot holds decoded block offset, in-block entry offset, fingerprint, and alignment padding. Lookup must still compare the complete byte key before returning the value. The data are immutable, so verification is paid once during construction.

The MPHF is PtrHash 2.1.2's DefaultPtrHash with default parameters and minimal remapping. Every full byte key is hashed with XXH3-128. The low word is the MPHF input and the high word supplies a 16-bit fingerprint. Every build rejects duplicate 64-bit input hashes and verifies one-to-one slot assignment. The prototype does not resolve a 64-bit collision. A real builder needs collision handling or seed retry plus validation. See the [PtrHash implementation and parameters](https://docs.rs/ptr_hash/2.1.2/ptr_hash/) and [paper](https://doi.org/10.4230/LIPIcs.SEA.2025.21).

For levels above L0, lookup binary-searches table maximum keys, checks the selected table's range, and then probes that SST's MPHF. L0 probes in descending file-number order. It never assumes all files are one SST. Non-overlap is asserted for each higher level. All source data have unique keys, Put records, and no snapshot history. There is no optional global SST maplet in this experiment.

The workload imports the existing readpath model and SplitMix function. Seed is 20261016. It measures the exact recall-by-id sequence `mix(seed ^ mix(1) ^ op) % 1000000`. The existing readpath has no negative workload. This experiment adds 1000000 to those IDs and uses the same key formatting. Because keys sort by agent and reversed ID, these misses cluster into 64 key-space gaps, one before each agent's existing ID range. Ordered indexes can serve those gaps from a small set of hot leaves. Their costs do not represent uniformly scattered interior misses or random-byte-key misses. They are not an adversarial fingerprint-collision workload.

Each backend copies the entire value into an owned Vec. LMDB begins and commits one read transaction per get, as in the existing backend. LMDB uses READ_ONLY against a private data copy with its own lock file, a 10 GiB virtual map, and normal reader locking. Native LMDB is pinned to the dataset's 0.2.5 version. Kiban opens its private copy through the unmodified public API with a 512 MiB block cache and default remaining options. MPHF's decoded bytes plus index fit inside 512 MiB; there is no eviction or cache-budget controller. The memory footprint excludes query vectors, allocator overhead, builder workspace, and the OS page cache. LMDB's 10 GiB virtual map is not a physical cache budget.

Before each process times lookups, it reads every existing key and compares its full value bytes with deterministic model output. It also checks negative keys before timing. After timing it validates every one of the million measured keys and full values, or absence for misses. The MPHF itself compares full stored byte keys on every successful get. An errors=0 result is emitted only after verification passes. Assertions abort the process and the runner stops on any failed subprocess.

Raw latency samples use precomputed byte keys. End-to-end samples include original key formatting and JSON-to-Memory parsing, covering the earlier benchmark's relevant work. LMDB additionally copies its mapped bytes before parsing, while the existing readpath backend parses directly from the mapped slice. That extra copy slightly favors MPHF in this end-to-end comparison; the raw comparison deliberately gives all backends owned results. Each has 100000 per-operation Instant samples, with exact percentiles. Both stop timing before result destruction. A separate batch loop measures one million independently generated keys, consumes and destroys results, and reports throughput. Perf enable/disable handshakes enclose only that batch loop. Hardware counters are user-mode CPU-core events: cycles, instructions, LLC-load-misses, dTLB-load-misses. They describe raw throughput, not the JSON sample loop. Exact percentiles are more precise than the existing histogram buckets, and timer/control differences mean absolute numbers need not reproduce the previous report exactly.

Each trial runs LMDB, Kiban, LMDB, MPHF, LMDB. Even trials reverse the candidate order. Five trials run independently for both layouts and both workloads. Within a trial, the three LMDB controls are reduced to their median; five such trial values produce the reported median and range. Candidate/control ratios are computed within each trial before reducing. Build time covers ten independent MPHF builds per layout, once for each hit and miss process. The total build timer includes mapping, checksums, block decoding, hashing, collision checks, MPHF construction, slot placement and occupancy validation. The MPHF-only timer is narrower. Both are proxies for compaction overhead; a real compactor already performs part of the total work.

Every timed run and MPHF construction uses CPU 8. Compilation uses `taskset -c 6,7,10,11 nice -n 10`, never concurrently with this tool's timed process. Driver processes use CPUs 6,7,10,11. CPU 9 is the sibling and receives no benchmark or build work, but unrelated browser and Btrfs kernel work run there. Per-CPU activity therefore disproves a fully idle sibling. No foreign process affinity or priority was changed. Other users' benchmark on 2-5 and crash sweep on 12-21 continue untouched. They share package power, LLC, and memory bandwidth, so this is CPU isolation on a loaded host, not a machine-wide quiet measurement. Metadata retains load, frequency, governor/EPP, and per-CPU counters before/after runs. Frequency policy is left unchanged. Interleaved controls reduce drift but cannot remove shared memory contention.

The 512 MiB floor is a random Hamiltonian cycle through cache-line-sized nodes. Dependent loads continue across chain boundaries, preventing overlap between requests. The report divides raw p50 by the length-1 floor only as a serial-load latency equivalent. This is not a measured count of dependent cache misses. MPHF commonly needs a pilot load, slot load, and record load, with occasional minimal-remap access. Pilot and level metadata may hit small caches; value copies span several lines. The larger paths also execute more instructions. The floor cannot prove an exact 2-3-load implementation or attribute all elapsed time to DRAM.

A production path still needs active and immutable memtable probes, version/snapshot acquisition and reference counting, newest-visible-version selection, tombstones, and crash-safe ownership of SST mappings. Its immutable-block verification must include any new metadata and must happen once before data become trusted. Range scans and latest-K queries still need sorted blocks and their existing ordering/index structures. MPHF construction and memory compete with compaction; production measurements must count that cost. This tool omits these paths by design. The result supports or rejects an isolated design direction, not a promised integrated-engine speedup.

LMDB itself uses a copy-on-write B+tree, as described by [its maintainer](https://www.symas.com/post.php?slug=is-lmdb-a-leveldb-killer). The premise that LMDB pages simply mutate in place is inaccurate. A static global locator would still need maintenance when records/pages move, while SSTs offer a natural once-per-output build lifetime. This experiment does not prove LMDB can never use perfect hashing, static indexes, a frozen snapshot, or an application-side accelerator. The conclusion is about these measured access paths, not architectural impossibility.

Allocator/page layout is part of this experiment. Opportunistic live `smaps_rollup` samples are retained in `memory-samples.jsonl`; these are not synchronized peak-memory measurements. Mimalloc-backed anonymous allocations use transparent huge pages on this host. The LMDB file mapping sample has no file PMD mappings, while anonymous Kiban allocations show substantial AnonHugePages. Therefore dTLB differences cannot be attributed to hashing alone. The prepared LMDB file is about 800 MiB and full verification touches it; 512 MiB is Kiban's block-cache setting, not a hard physical memory cap imposed on LMDB. The MPHF footprint is its decoded arena plus locator metadata, not all resident pages in the process or host. These are properties of the supplied baseline and allocator, and should be controlled separately before claiming that dependent-address count alone explains the full speedup.

The start floor is not interleaved with each variant and probably benefits from anonymous transparent huge pages. LMDB's file-backed mapping has different TLB behavior. Its load-equivalent number includes page-walk and software overhead, so it cannot be read as a physical dependency count. A second floor after the full suite checks time drift, but does not equalize page layout.

There is no sorted/fence-search control over the same decoded arena. The measured benefit belongs to the combined decoded-block + MPHF access path, including removal of the block-cache lookup and prefix decoding. These results cannot isolate the MPHF's contribution from those other changes. Bulk has exactly one L0 SST, so per-SST routing is a degenerate single-table case there. The normal layout, with one L1, six L2, and 77 L3 tables, exercises actual multi-level per-SST routing.
