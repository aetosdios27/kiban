# Frozen before screening

The question is whether Kiban's warm, single-worker keyed JSON memory API is faster than a tuned RocksDB configuration with equivalent payloads, and which tradeoffs remain after tuning. No winner is assumed. This is not an engine-throughput, cold-disk, vector-search, or steady-state-write test.

Seed 20261016, 64 agents, 200-byte ASCII text, immutable creation sequence and revised JSON values. Point reads reuse default ReadOptions and use get_pinned_opt, without a fixed snapshot. Each latest-K call creates a fresh iterator and ReadOptions, as required by the safe rust-rocksdb iterator ownership API. Same keys (`agent/NNNN/memory/<u64::MAX-id padded to 20 digits>`) and same serializer. Existing full-payload oracle runs before and after each command; each timed read result and each write readback is checked outside its timer. Writes reopen and verify the final model.

Eight complete RocksDB candidates: Bloom 10 bits/key or Ribbon at Bloom-equivalent 10 bits/key; 4 KiB or 16 KiB blocks; prefix seek or total-order seek. Fixed 11-byte agent prefix, whole-key and prefix filter entries, 0.1 memtable prefix Bloom ratio, binary-and-hash data-block indexes, cached index/filter blocks and pinned L0 index/filter blocks. No compression in screens. Default RocksDB leveling, 64 MiB write buffer, two background jobs; WAL enabled with default automatic flushing to the OS. All remaining defaults are retained in OPTIONS receipts.

For reads and writes separately, choose the minimum equal-workload geometric mean of five-trial medians of mean call time. Read score includes both API calls × bulk/normal × explicit 512 MiB/default cache budget. Write score includes remember/update/mixed × fast/durable. Pick one complete configuration per family, never individual operation winners; ties use label order. Each scenario has five rotated trials and LMDB each trial. All losing screens are retained. The selection is frozen before primary measurements. Separate LZ4 rows use the corresponding read/write winner; no-WAL fast writes use the write winner. Optional mmap and row cache are omitted.

Read population 1M, 100k calls per operation. Bulk RocksDB uses one externally built sorted SST ingested into the deepest available level. Kiban bulk uses its original bulk loader and one flush. Normal RocksDB uses individual ID-order puts with automatic compaction enabled, then flushes and waits for scheduled compactions to settle. No forced full compaction is added to the normal layout. Kiban normal uses its existing default write-buffer flush policy and compaction picker. Tables, levels, pending bytes and active jobs are retained. Each fixture stays fixed across all trials. Write population 10k; fresh fixture copy for every command; 1k calls in each of five stages, exactly 2100 mutations.

All preparation, measured engines, diagnostic engines and their threads are pinned to CPU 10. CPU 11 activity and host load are recorded. This task never assigns work to CPU 11 or CPUs 3/4, 6/7, 8/9. Coordinators run on 12–21; builds/tests on 12–21 at nice +10, completed before timed runs. No profiler or sync probe overlaps primary timings. The host is shared; affinity is not exclusive reservation.

Report p50/p99/mean-call throughput, verified throughput, ranges, same-round ratios against RocksDB and LMDB, post-process logical/allocated bytes and whole-process peak RSS. Histogram percentiles are upper bucket bounds (<3.125% relative bucket error above 32ns). Returned Memory destruction is outside timers. No global page-cache drops; full verification warms every fixture. Cache bytes are matched, total resident memory is not. LZ4 is a labeled compression tradeoff; no-WAL is a no-durability tradeoff. Durable writes sync each mutation. WAL-on `sync=false` is stronger against process death than Kiban fast's userspace-buffered acknowledgments. Final persistence is outside operation timers and cannot strengthen an earlier acknowledgment.
